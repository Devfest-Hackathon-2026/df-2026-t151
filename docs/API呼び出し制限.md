# API呼び出し制限

2026年11月10日更新。提出・審査時の利用のため、Cookieごとの毎分・日次上限とプロセス全体の毎分上限を従来の100倍へ引き上げた。同時処理上限は維持する。

2026年11月9日。ユーザー指定により、初期対応はCookieを使い、Firestoreによる共有制限は次の作業とする。追加のクラウド設定・依存ライブラリは不要。

## 今回の実装

| 対象           | Cookie識別子ごとの毎分上限 | 日本時間の1日上限 |
| -------------- | -------------------------- | ----------------- |
| 場所検索       | 2,000回                    | 10,000回          |
| 寄り道候補検索 | 300回                      | 1,000回           |
| 行程の再検証   | 1,000回                    | 3,000回           |

数値は初期運用の暫定値で、`src/server/cookie-rate-limit.ts`の`COOKIE_LIMITS`で変更できる。分の枠は毎分00秒、日の枠は日本時間0時にサーバー時刻で切り替わる。選択済みの行程を再検証できるよう、3種類を別枠にする。health・capabilities・画面閲覧は対象外。

入力検証後、既存のプロセス全体の制限と外部API処理へ進む前に回数を同期的に確保する。入力不正は数えず、確保後の外部障害・中断・既存の混雑制限は試行として数える。検索結果0件も数える。プロセス全体では場所検索6,000回/分・同時4件、候補検索と再検証合計2,000回/分・同時2件を上限とする。Google側のクォータとCloud Runの最大インスタンス数・同時リクエスト数は今回変更しない。

上限到達時はHTTP 429・RATE_LIMITED・Retry-Afterと、相関するrequestIdを返す。既存の画面クライアントがエラーメッセージを表示するため、共通JSON・型・fixtures・画面部品は変更しない。日次上限は「明日0時（日本時間）以降」、毎分上限は「1分ほど待って」と案内する。

Cookie `yorimichi_usage`はランダム識別子とHMAC-SHA256署名だけを持つ。回数はCookieに入れず、署名付きの過去Cookieを再送しても同じプロセスでは回数が戻らない。署名は既存のOPTION_TOKEN_SECRETを用途別の文字列とともに使い、未設定のローカル環境ではプロセス内のランダム秘密値を使う。不正・重複・過大なCookieは、識別子を登録できるときに再発行する。

CookieはHttpOnly・SameSite=Lax・Path=/・Domain未指定・有効期間30日。HTTPSではSecureを付け、HTTPのローカル開発では付けない。位置・検索語・到着日時・地点ID・履歴をCookieや回数表へ保存しない。サーバーでは識別子に操作種別・時間枠・回数だけを関連付け、日替わり後の最初の照会で前日の回数表を破棄する。

### 記録テーブルが満杯になった場合

記録は1プロセス10,000識別子まで。満杯時は既に記録している識別子の枠を維持し、未登録のリクエストはCookie単位の記録と新規発行を省略して、プロセス全体の毎分・同時処理制限へ進める。署名が有効でも、当日の回数表に登録されていない識別子は同じ扱いになる。日替わり後は登録とCookie発行を再開する。

## 制約

- Cookie削除・無効化・別ブラウザ・シークレットモードでは別の利用枠になる。Cookieを持たない同時初回要求も別枠になり得る。本人確認やボット防御ではない。
- 回数はプロセス内なので、再起動・新リビジョン・別インスタンスでは共有されない。最大1インスタンス設定でも永続的な制限とはならない。
- 1回の操作は複数の有料APIを呼ぶ。今回の操作回数制限は、サイト全体の費用やGoogle側の呼び出し総数の上限を保証しない。
- ログ・IAM・APIキー・Cloud Run設定は変更しない。本番への反映状況は公開記録で別に管理する。
