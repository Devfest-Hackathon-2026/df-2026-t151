# 拡張性と設計

よりみちは、画面とAPIの契約を共有し、候補の取得・計算・選定を分けている。既存の応答形式で表現できる寄り道体験や選定方針の変更は、同じ画面に反映できる。

## 機能追加を支える構造

### 画面とAPIの境界

場所検索・候補検索・行程再検証の入出力は、画面とサーバーが参照する共通の型で定義している。ブラウザの通信と応答の検査はAPIクライアントに集約している。例えば、候補の並べ方を変える場合は、既存の応答形式を保ったままサーバー側の選定を変更できる。[共通型](../src/lib/api/types.ts) · [APIクライアント](../src/lib/client/planner-api.ts)

### 候補検索の工程

候補検索の起点で各工程の順序を管理し、候補の絞り込み、経路の取得、結果の組み立てを別のモジュールに分けている。天候予報を取得する処理と、予報を比較して候補を除外・並べ替えする判断も分かれている。天候による優先順位を変える場合は、選定側に変更を集約できる。[候補検索](../src/server/detour-search.ts) · [予報の取得](../src/server/visit-forecasts.ts) · [天候による選定](../src/server/weather-selection.ts)

### 体験カテゴリと時間見積もり

カフェ・軽食・小規模展示の体験時間と待ち時間の目安を、カテゴリ別のプロファイルに集約している。既存カテゴリの目安を調整するときはプロファイルを更新する。新カテゴリを追加するときは、Geminiの候補抽出条件と、利用可否や体験内容を評価する処理も更新する。[体験プロファイル](../src/server/experience-profiles.ts) · [候補抽出条件](../src/server/grounded-detours/requests.ts) · [利用可否の判定](../src/server/candidate-access.ts)

### APIの共通処理と外部依存の差し替え

候補検索と行程再検証では、本文の読み取り、エラー応答、回数制限を共通のハンドラーで処理する。各ルートは入力検証と実行する処理を渡す。候補取得・経路計算にテスト用の関数を渡せるため、Google APIを呼ばずに選定の挙動を検証できる。[共通ハンドラー](../src/server/planner-post-handler.ts) · [候補検索ルート](../src/app/api/v1/recommendations/route.ts) · [行程再検証ルート](../src/app/api/v1/itineraries/validate/route.ts) · [候補検索のオプション](../src/server/detour-search/types.ts)

## 追加設計が必要な範囲

- **移動手段の追加**。共通型は徒歩・公共交通・車・自転車を表せる。現行の対応は徒歩で、別の手段を提供するには、対応手段の通知、入力検証、経路計算、画面表示を揃える必要がある。[対応手段の通知](../src/server/api-capabilities.ts) · [経路計算](../src/server/routes.ts)
- **利用者増加に伴う複数インスタンス運用**。Cookieごとの利用回数とプロセス全体の呼び出し枠は、プロセス単位で管理している。インスタンスを増やす場合に同じ利用枠を適用するには、回数の共有と同時更新の制御が必要になる。Firestoreを使った共有制限は今後の設計項目として記録している。[API呼び出し制限](API呼び出し制限.md)
