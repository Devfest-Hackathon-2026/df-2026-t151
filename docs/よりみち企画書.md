# よりみち（仮称）企画書

作成日：2026年11月7日／初版。大会情報はPROJECT_MEMORY.mdを参照。本書の機能・技術・効果は企画案であり、未実装・未検証。

### 方針更新（同日）

追加：天候・現在時刻・混み具合もユーザーに質問せず候補選定に利用する。現在時刻は自動取得し、天候は外部API、混雑は取得可能な外部情報を使う。訪問予定時間帯の情報を優先し、混雑の観測・傾向・推定・不明を分ける。情報取得不能時は不明と表示して検索を継続する。詳細は要件定義書0.3を参照。

ユーザー指定により、観光地点を一から登録する前提を撤回。候補・施設情報・経路計算はGemini APIやGoogle Maps関連APIで取得する。本文中の「確認済み候補8〜12件」「チームが管理する地点データ」は旧案であり、事前登録は不要。最新要件は「よりみち要件定義書.md」冒頭の改訂を参照。人手は接続設定とサンプル検証に使う。Geminiで提案を作り、経路APIの時間とアプリの期限比較で行程を確認する。差別化は、3入力から比較・選択・行程反映までの手軽さとして検証する。

## コンセプト

**目的地までの空き時間を、その土地の思い出に変える。**

国内観光中のユーザーが「目的地」「到着したい時刻」「現在の移動方法」を入力すると、現在地から目的地までの移動に、時間内に楽しめる寄り道を組み込む。単に近くの施設を並べず、何を楽しみ、どれくらい滞在し、いつ出発するかを一つの行程として提示する。

## 対象と課題

### 対象エリア：新宿（ユーザー決定）

初版の対象エリアは新宿とする。ユーザーのキャンパスが新宿にあることが選定理由。開発上は、身近な地域で候補地・徒歩経路・体験時間を現地検証しやすい点を活かす。これは選定理由に対する開発上の解釈であり、検証実施済みを意味しない。

新宿区全域を対応範囲とするか、新宿駅・キャンパス周辺等に絞るかは未確定。キャンパスの名称・位置は推測しない。国内観光客の利用場面を対象とし、学生向けサービスへ変更するものではない。候補は外部APIで動的に取得し、有効な登録済み体験時間があれば優先する。

国内観光中、ホテルのチェックイン、食事の予約、待ち合わせなど、次の予定まで時間がある人。年齢や家族構成で限定せず、旅行先での具体的な利用場面を対象にする。

課題仮説：少し観光したくても、近隣の検索、営業時間確認、寄り道後の移動時間の計算が必要で、遅刻への不安から目的地へ直行してしまう。困りごとの頻度と現状の対処は利用者に確認する。

## 入力

必須入力はユーザー指定の3つ。

1. 目的地：次の予定の場所。
2. 到着したい時刻：その場所に着いていたい日時。当日を初期値とし、翌日なら明示する。
3. 現在の移動方法：徒歩・公共交通・車・自転車を想定。ただし初版の対応範囲は後述。

現在時刻は端末から取得。現在地は本人の許可を得て取得し、取得できない場合だけ出発地点を手動指定する。好みの長いアンケートや会員登録は初回の必須操作にしない。

## 利用体験

1. 3項目を入力し、現在地を確認する。
2. 直行する場合の移動時間と、余裕を残して使える時間を表示する。
3. 時間条件に合う寄り道を最大3案表示する。余裕がなければ直行を案内する。
4. 気になった案を選ぶと、現在地→寄り道→目的地の行程を表示する。
5. 寄り道先では見どころと出発目安を確認できる。時間が減った場合は、ユーザー操作で現在地から再計算する。

### 説明用の架空例

現在14:00、目的地はホテル、到着希望15:30、徒歩。ある寄り道案の移動合計が30分、体験が35分、余裕が25分なら90分に収まる。

「地元のおやつを買って、川沿いの景色を楽しむ」という体験カードに、追加移動、滞在目安、概算費用、目的地への到着見込みを表示する。時間・施設・費用は実データに置き換えて検証する。

## 楽しさの設計

候補は「食べる」「景色を見る」「土地の文化に触れる」など異なる体験として比較できるようにする。

- 地元の一口：地域らしい食べ物を短時間で楽しむ。
- 一枚の景色：立ち寄って撮影したくなる景観を見つける。
- 町の小さな発見：建物や史跡の見どころを、現地で確かめる。

名称は体験を伝えるための例。謎解き・写真投稿・ポイント獲得を必須にしない。観光資源とのつながりを明確にし、地域情報は確認済みの事実を使う。前の会話で提案した冒険・ミッション形式は、現時点では未採用の追加候補。

## 差別化の仮説

Google検索やGeminiでも場所探し・行程相談はできる。独自機能が存在しないとは主張しない。本案は、次の体験を少ない操作で完了できることを目指す。

- 到着時刻と移動方法を毎回文章で説明せず、空き時間に合う候補を比較できる。
- 寄り道の追加移動と現地で楽しむ時間を分けて示す。
- 「何ができるか」「いつ切り上げるか」「何時ごろ目的地に着くか」を一画面で判断できる。

差別化は機能表だけでなく、通常の検索・Geminiとの比較で判断時間、操作負担、条件の見落としを測る。

## 時間と推薦の考え方

候補ごとに「現在地→寄り道の移動＋滞在＋寄り道→目的地の移動＋余裕時間」が残り時間以内かを確認する。直行所要時間を引くだけでは、寄り道による遠回りを評価できないため、候補経由の全区間を扱う。

営業時間、最終入場、確認済みの滞在目安も判定する。初版は寄り道1か所を基本とし、余裕時間は仮設定から実地検証で見直す。経路や営業情報が不足する候補は推薦から外す。混雑・交通事情で変わるため、到着見込みを保証とは表示しない。

## ハッカソン用の最小実装

- 一つの観光エリア、確認済みの候補8〜12件。
- 3入力、候補比較、行程確認の一連の操作。
- 初版は徒歩対応を確実に完成させる。移動方法の項目は残し、未対応の方法を選ぶと対応状況を明示する。徒歩へ勝手に読み替えない。
- 候補なし、現在地取得失敗、外部サービス失敗への対応。
- 各地点の出典、情報確認日、素材の利用条件を記録する。

公共交通は便・待ち時間、車は駐車と降車後の徒歩、自転車は駐輪と通行条件が必要になる。これらは徒歩と同じ時間計算で処理せず、データを確保できた順に追加する。全手段対応は将来像であり、初版の完成条件と分ける。

## Google技術の構成案

- Cloud Run：WebアプリとAPIの実行基盤。大会の必須基盤条件への対応候補。
- Google Maps Platform：地図・経路・施設情報の取得候補。交通手段別の提供範囲、料金、表示・保存条件は実装前に公式資料で確認する。
- Gemini：確認済みの施設情報から短い体験説明を作る補助。営業時間や経路時間は生成させず、通常の処理で判定する。AIが使えなくても候補比較を継続できる構成を目指す。

技術はまだ確定していない。採用理由、代替案、費用・遅延・運用上の制約を開発時に記録する。Google技術が課題解決のどこに必要かを説明できる構成とする。

## 安全性と情報の扱い

位置情報は利用目的を示して取得し、初版では移動履歴の継続保存をしない。APIキーは公開せず、利用制限と費用上限の設定を確認する。行列が読めない購入体験などは不確実性を明示する。移動中の操作を促さず、立ち止まって確認できる画面にする。

## 検証と成功の目安

国内旅行経験者3〜5人に、実際に空き時間が生まれた場面と対処を聞く。その後、同程度の旅行課題で通常検索・Geminiと試作品を比較する。

- 寄り道を選ぶまでの時間と操作負担。
- 時間・営業条件に反した案の件数。
- 「実際に寄りたい」と思う候補があった割合。
- 現地試行での移動・滞在の見積もりと実測の差。

仮目標は「入力後1分以内に寄りたい候補を選べる」。実際の結果と分けて扱う。短期テストだけで混雑緩和や地域消費増加を実証したとはしない。
