## 体験時間の取得と計算（最新版）

この節は本文の滞在時間・時間式に優先する。2026年11月7日の作業領域確認では、企画文書のみが存在し、登録済みの体験時間データ、アプリ実装、外部API接続設定は確認できなかった。現段階の確認は要件と公開API仕様の確認であり、実動作検証ではない。

### 取得の優先順位

| 順位 | 体験時間の情報源                       | 採用条件                                                                                                                                                        |
| ---- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | こちらで登録済みの地点・体験別データ   | 同一地点・同一体験を特定でき、有効期間・適用条件を満たすこと。出典・確認日を持ち、古い値や別コースの値を無条件に優先しない                                      |
| 2    | 施設公式サイト、観光協会等の外部データ | 同じ体験の所要時間であることを確認する。Geminiの検索グラウンディング等で取得する場合も、根拠URLと該当情報を保持する。営業時間や移動時間を体験時間と取り違えない |
| 3    | 外部サービスの滞在時間データ           | 対象地域・地点の対応、取得可能性、利用条件を確認して採用する。統計的な平均滞在は、短縮可能な最小体験時間とは扱わない                                            |
| 4    | カテゴリ・体験内容からの推定           | 根拠のある値が取れない場合に限る。カテゴリの目安またはGeminiの構造化された時間範囲を使い、「推定」と表示する。計算には範囲の上限を使う                          |

地点名だけでなくplace ID等と体験の識別子を照合する。同じ美術館でも「外観撮影」と「館内鑑賞」は別の体験。登録は任意の補足・補正用とし、全候補を事前登録する必要はない。施設の最新の閉鎖・営業情報は時間データの優先順位とは別に検証する。

推定でも妥当な時間を設定できない場合は推薦から外す。予約や開始時刻が固定されたプログラムは、所要時間だけで判断せず参加可能な開始時刻・予約条件も検証し、確認できなければ初版では除外する。

### データ項目

地点ID、体験ID・内容、所要時間の下限・上限（分）、待ち時間を含むか（含む／含まない／不明）、出典種別・URL、確認・取得日時、有効期間、適用条件、実測・公式記載・統計・推定の区分を保持する。範囲の逆転、負数、単位欠落、地点不一致は採用しない。

### 計算

**必要時間＝現在地→寄り道の移動＋待ち時間＋体験時間＋寄り道→目的地の移動＋余裕時間**

必要時間が到着希望日時までの残り時間以内である候補を採用する。体験時間を空き時間に合わせて勝手に短縮しない。短縮版を出す場合は、別の体験として必要時間とできる内容を定義する。

待ち時間を含む所要時間は二重加算しない。含有範囲が不明な場合は内訳不明とし、重複の可能性を残した保守的な計算であることを示す。待ち時間が取得できない場合は0分という事実を作らない。2026年11月9日のユーザー合意により、カフェ・軽食・小規模展示は種類別の推定待ち時間幅の上限を含む暫定候補として扱う。入場・注文の待ちが不可避で、推定幅も設定できない候補は除外する。実測の混雑と区別し、推定上限を実際の保証上限と表示しない。内訳・条件は[飲食と館内体験.md](飲食と館内体験.md)に記録する。

寄り道到着＝t0+a、体験開始＝t0+a+w、出発＝t0+a+w+s、目的地到着＝t0+a+w+s+b。ここでwは重複を除いた待ち時間。営業・最終入場は待ち時間を加味した実際の入場見込みと照合し、体験終了が利用可能時間内に収まることを確認する。余裕mは到着見込みと分けて表示する。

### 受け入れ確認の追加

- 有効な登録値30分と外部値45分があれば、登録値30分を採用し、情報源を表示する。
- 登録値が別体験・期限切れなら除外し、外部データへ進む。
- 外部値20〜40分なら、40分で期限を判定する。
- 移動合計30分、体験30分、待ち15分、余裕10分なら必要85分。残り80分では除外する。
- 上の体験30分が待ち15分を含む総時間なら、必要70分として二重加算しない。
- 体験時間不明、取得失敗、推定の区分を表示し、空き時間に合わせた架空の短縮をしない。

### 外部仕様確認

Google Mapsでは滞在時間や待ち時間が表示される場合があるが、Places APIの公開Placeスキーマでは汎用的な体験所要時間フィールドを確認できなかった。Mapsの表示をそのままAPIで取得できる前提にはしない。

参照（2026年11月7日）：https://support.google.com/business/answer/6263531 、https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places 。取得先の接続・具体地点での検証は実装時に行う。

## 追加要件：ユーザーに問わない周辺状況

ユーザー指定により、天候・現在時刻・混み具合も候補探索に使う。必須入力は目的地・到着希望時刻・移動方法の3つのまま。以下は追加要件であり、本文の「混雑予測は対象外」は独自予測システムの開発を対象外とする意味に更新する。

| ID  | 情報       | 取得・利用要件                                                                                                                                                                                |
| --- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C01 | 現在時刻   | 自動取得し、日時と現地タイムゾーンを保持する。検索・選択・再計算時に更新する。期限と営業判定を同じ時間基準で比較する                                                                          |
| C02 | 天候       | Weather API等から現在地・寄り道先の現在天候と訪問予定時間帯の予報を必要な範囲で取得する。雨なら屋内候補を優先、強風等では影響を受ける体験の順位を下げる。屋内属性不明の地点を屋内と断定しない |
| C03 | 混雑       | 利用可能な外部データがあれば順位・時間余裕に反映する。リアルタイム観測、過去傾向、一般的な時間帯の推定、不明を分ける。すべての施設で取得できる前提にしない                                    |
| C04 | 説明       | 「訪問予定時刻に雨予報のため屋内を優先」等、選定理由と情報取得時刻を表示する。API情報とAI推定を区別する                                                                                       |
| C05 | 欠損・障害 | 天候・混雑の取得失敗だけでは検索全体を停止しない。不明と表示し、時間・経路・営業等の取得できた情報で候補を出す。不明を晴天・空いている状態へ変換しない                                        |

### 判定と優先順位

まず移動・滞在・到着期限・営業の条件で候補を絞り、その中から天候適合性、混雑による不確実性、体験の違いで並べる。混雑のため時間に収まらない根拠が得られた案は除外する。閉鎖・運休等の明示情報を取得した場合も該当案を除外する。

観測待ち時間の数値は、提供元が待ち時間として示したものを使う。対象の飲食・館内体験では、ユーザー合意の種類別推定幅を別区分で加算できる。「混んでいる」割合から待ち時間を独自に換算しない。観測・推定とも到着時の保証とは扱わず、Geminiの推測を実測混雑としない。経過時間の初期対応は再計算時の現在時刻・最新出発地点による残り行程の再評価で、体験開始・滞在経過分の自動計測はしない。

### データと取得制約

天候・混雑に、対象座標または地点ID、情報種別、観測・予報対象時刻、取得時刻、提供元、取得状態を保持する。保存期間・帰属表示は提供元の条件に従う。

Google Maps画面の混雑表示を、Places APIでそのまま取得できるとは想定しない。採用するAPI・SDKの取得可能項目と用途を接続検証する。リアルタイム混雑の取得先が締切までに確保できない場合は「傾向・推定・不明」による初版とし、実測対応を実装済みと説明しない。

### 追加の受け入れ確認

- 雨予報かつ屋内・屋外の時間適合候補がある場合、屋内案が優先され、理由が表示される。
- 現在晴れていても訪問時間帯が雨予報なら、訪問時間帯を基準にする。
- 天候または混雑API停止時も取得済みの経路等で検索を継続し、不明を表示する。
- 混雑傾向だけの候補を「現在空いている」と表示しない。
- 信頼できる待ち時間を加えて期限を超える候補は除外し、待ち時間が不明ならゼロ分確定と表示しない。

参照（2026年11月7日）：https://developers.google.com/maps/documentation/weather/overview 、https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places 。具体的な気象閾値と混雑提供元は実装時に確定する。

## 改訂：外部APIを中心とする開発方針

ユーザー指定により、観光地点を一から手作業で登録する方式を採用しない。候補探索、場所情報、経路時間は外部APIを活用する。以下の記述は本書の手動登録・確認済みデータ前提に優先する。

- 候補取得：Gemini APIのGoogle Mapsグラウンディング、またはPlaces APIで動的に取得する。事前登録8〜12件を完成条件から外す。対象地域は検証範囲として絞れるが、登録済み地点のみを検索する設計にしない。
- 経路時間：Routes API等の経路サービスから取得する。Geminiの文章内の推定時間だけで「間に合う」と判定しない。全区間の加算・期限との比較は小さな通常処理で行い、経路計算自体は自作しない。
- Geminiの役割：候補探索、地域らしい体験の構成、比較しやすい説明の生成。実在地点と出典の対応を検証する。構造化された場所情報が不足する場合はPlaces API等で補う。
- 営業情報：APIから取得した情報と取得時刻を表示する。現地確認済みとは表示しない。営業時間を取得できない施設は初版の時間適合候補から除外する。取得・保存・表示条件を守る。
- 滞在時間：APIが保証する値とは扱わない。まず短時間の立ち寄り向けのカテゴリ別目安を使い、推定と表示する。行列や予約が前提となる長時間体験は初版で優先しない。
- AI停止時：取得済みの有効な構造化情報があれば名称等による簡易表示に切り替える。候補を取得できていない場合は検索失敗として再試行を案内し、存在しない固定候補を出さない。
- 地点管理画面・観光地点台帳は不要。外部APIの情報、必要な帰属表示、使用API・ライブラリの利用条件を管理する。人手はAPI設定、実際の候補・経路のサンプル検証、出典表示の確認に使う。
- データ要件の観光候補は「事前登録する台帳」ではなく検索時の応答データと読み替える。APIで取得できない費用・最終入場等は不明状態を保持し、AIで補完して確定事実にしない。利用可否判断に必要な項目が不明なら候補から外す。
- 性能目標・タイムアウトは外部呼び出しの実測で見直す。モデルとツールの組合せ・出力形式・日本での移動手段の対応は接続検証後に確定する。

差別化の検証対象は「3項目で開始し、移動込みの寄り道を比較・選択して行程に反映できる操作体験」。独自データの保有やGeminiにはできない処理を価値の前提にしない。単に同じ質問を転送するだけで終わらず、時刻・経路の検証と選択後の行程をアプリ側で扱う。

参照（2026年11月7日確認）：https://ai.google.dev/gemini-api/docs/maps-grounding 、https://developers.google.com/maps/documentation/routes/ 。APIによる裏付けも情報の完全性や到着を保証しない。

## 1. 目的と対象

国内観光中、次の予定まで時間がある人が、目的地への到着を考慮しながら、その土地らしい寄り道を選べるようにする。

ユーザーが指定した確定の軸は「目的地・到着したい時刻・現在の移動方法」の入力と、その隙間時間の活用。年齢や家族構成による限定はしない。単なる散歩案内ではなく、地域の食・景観・文化に触れる観光体験を扱う。

## 3. 用語

- 目的地：寄り道後に到着したい次の予定の場所。
- 到着希望日時：目的地に着いていたい日時。当日を初期値とし日付を確認できる。
- 直行時間：現在地から目的地へ寄り道なしで移動する見積もり。
- 余裕時間：移動の誤差などに備えて予定に確保する時間。初版の仮値は10分とし、実測で見直す。公式基準ではない。
- 寄り道可能：全移動、滞在、余裕時間が残り時間に収まり、営業等の条件も満たす状態。到着の保証を意味しない。

## 5. 候補選定と時間計算

計算基準時刻を t0、到着希望日時を D、現在地から候補までの移動を a、候補から目的地までを b、滞在を s、余裕を m とする。

**採用条件：t0 + a + s + b + m ≦ D**

- 寄り道到着見込みは t0+a、出発目安は t0+a+s、目的地到着見込みは t0+a+s+b。
- 追加移動時間は (a+b)−直行時間。直行時間と条件・取得時刻を揃える。負値等の矛盾はデータを確認し、黙って補正しない。
- 直行でも間に合わない場合は、その見積もりを伝え、寄り道を提示しない。
- 開店前の到着、閉店を超える滞在、最終入場後の到着、休業日の利用は除外する。初版では開店待ちを組み込まない。
- 経路が取れない、営業時間や利用可能条件を確認できない地点は除外する。公園等は確認済みの利用可能時間として登録する。
- 検索後も時間が経過するため、選択・再計算時に最新時刻で条件を再検証し、成立しなくなった案は行程として確定しない。
- 全件を条件で絞り天候で評価した後、有効な外観観察の最上位を先頭の必須枠にする。残り2枠には飲食・館内体験を優先し、追加体験が不足する場合は他の有効な外観候補で補う。各分類内の時間・天候順位は維持する。外観が1件も成立しなければ、飲食だけの提案は返さない。危険な天候・利用条件不明等を必須枠のために緩めない。
- 初版では渋滞・行列のリアルタイム把握を前提にしない。待ち時間の不確実性は表示し、到着保証をしない。

## 6. 画面要件

候補カードは1枚ずつ横に切り替える。複数件では左右スワイプ・前後ボタン・位置を示すドット・件数を用意し、キーボードでも移動できるようにする。自動再生はしない。1件なら切り替え操作を表示せず、0件なら理由と直行・条件変更の操作を維持する。新しい検索結果は先頭から表示し、外観必須枠の並び・推定や出典の表示・選択時の再検証は維持する。ページ全体の横はみ出しは防ぎ、候補領域の横操作のみを許可する。

行程画面には「Googleマップで徒歩ルートを開く」を置く。寄り道ありは出発地点→選択した寄り道→目的地、直行は出発地点→目的地とする。再計算・訪問完了後は表示中の最新行程からリンクを組み直す。クリックするまで外部地図は開かず、地点をGoogleマップへ渡すことを説明する。Googleマップの経路・移動時間は別に再計算され、アプリの滞在・余裕時間や到着期限は引き継がない。

| 画面     | 必要な要素                                                                              |
| -------- | --------------------------------------------------------------------------------------- |
| 条件入力 | 目的地、到着日付・時刻、移動方法、現在地確認、検索、位置取得不能時の手動入力            |
| 候補比較 | 条件の要約、直行見積もり、最大3件の体験カード、時刻と所要時間、条件変更、候補なしの案内 |
| 行程確認 | 選択した体験、全区間と時刻、見どころ、出発目安、情報出典、再計算、寄り道をやめる操作    |

読み込み中・入力エラー・通信エラーを画面内に表示する。二重検索は防ぎ、以前の遅い応答で新しい結果を上書きしない。

## 9. 技術選定とAIの境界

Cloud Run、Google Maps Platform、Geminiは企画段階の候補。具体的API、対応移動方法、料金、制限、利用条件は実装時に公式資料で確認する。本書は未確認のAPI機能を前提としない。

Google技術を中核に使う理由、比較した選択肢、受け入れる制約を記録する。Geminiは確認済み情報の体験説明に利用できるが、座標、営業時間、経路時間を生成して事実扱いしない。AI応答失敗時は確認済みの固定説明を使い、時間計算と候補比較を継続する。最終的に寄り道を選ぶのはユーザー。
