# GitHub運用ルール

2026年11月7日。2人開発の共通ルール。大会の公式ルールではない。

## 1. 基本方針

- mainは共有・提出の基準。作業はブランチで行い、Pull Request（PR）を通して統合する。mainへの直接Pushはしない。
- developや個人専用の長期ブランチは作らず、1作業1ブランチを基本にする。
- 作業ブランチへのPushは途中でも可能。未完成ならDraft PRにする。
- 完成後、相手が内容・確認結果を見て承認し、Squash and mergeでmainへ統合する。コミットを1つにまとめ、PRタイトルを統合メッセージに使う。
- Codexは依頼範囲の実装・コミット・作業ブランチへのPushを行えるが、相手の承認を代行しない。mainへのマージ・公開は人が判断する。

## 2. ブランチ名

形式：`種類/担当範囲-作業内容`。英小文字・数字・ハイフンを使う。担当範囲はui／api／infra／docs／shared。人名は不要。Issue番号があれば末尾へ付けてもよいが必須にしない。

| 種類     | 用途               | 例                                                 |
| -------- | ------------------ | -------------------------------------------------- |
| feat     | 機能追加           | feat/ui-destination-form、feat/api-recommendations |
| fix      | 不具合修正         | fix/api-duration-double-count                      |
| docs     | 文書変更           | docs/docs-git-workflow                             |
| chore    | 環境・依存・設定   | chore/infra-docker-setup                           |
| refactor | 挙動を変えない整理 | refactor/api-route-client                          |
| test     | 検証コード         | test/api-time-boundaries                           |

既存の`setup/shared-environment`は作成済みの例外としてそのまま使い、新規ブランチから命名を適用する。公開済みブランチの改名は不要。

## 3. コミットメッセージ

形式：`種類(範囲): 変更内容`。範囲はui／api／infra／docs／shared。種類は上の表と同じ。説明は日本語を基本とし、1行で変更後の動作を具体的に書く。長い理由や制約は空行を挟んだ本文、またはPRへ記載する。

例：

```text
feat(ui): 目的地と到着時刻の入力画面を追加
feat(api): 経路時間を使って寄り道候補を絞り込む
fix(api): 待ち時間込みの体験時間の二重加算を修正
docs(docs): GitHub運用ルールを追加
chore(infra): Cloud Run用の起動設定を追加
```

「修正」「update」「いろいろ変更」だけの説明は避ける。1コミットは説明できる一つの変更を基本とし、無関係な変更をまとめない。AI生成であることをタイトルへ毎回入れる必要はない。AIに任せたことと人間の判断は別途記録する。

## 4. Push前の確認

1. `git status`と差分で、現在のブランチと対象ファイルを確認する。
2. 変更したファイルを明示して追加する。無確認の全ファイル追加は避ける。
3. キー・.env・正確な位置履歴・生成物が含まれないことを確認する。
4. コード変更は本番ビルド・型チェック、時間計算変更は境界値も確認する。文書のみなら差分・リンク・形式を確認し、不要なインストールは行わない。
5. API変更は仕様・仮データ・共通型を揃え、相手側への影響をPRへ書く。

インストール・ビルドを保留する場合も、作業ブランチへのPushは可能。PRの確認欄へ「未実施」と理由を書き、未検証のコードを検証済みとしてmainに統合しない。確認した文書変更はコード検証を待たずにレビューできる。共通開発環境については2026年11月7日に依存の固定・ビルド・型チェックを完了し、GitHub Actionsの成功も確認済み。検証の詳細と未確認範囲は検証結果.mdを参照する。

Force Pushは禁止。共有済みの履歴をrebaseで書き換えず、追加コミットで直す。どうしても履歴変更が必要な場合は相手と事前調整し、通常ルールの例外として扱う。秘密情報をPushした場合は履歴修正だけで済ませず、まずキーを失効・再発行する。

## 5. 作業開始と更新

未コミットの作業がないことを確認して実施する。作業中なら先に現在の変更を安全にコミットする。

```sh
git switch main
git pull --ff-only origin main
git switch -c feat/ui-destination-form
```

初回Push：`git push -u origin feat/ui-destination-form`。以降は同じ作業ブランチへPushする。PR作成後の修正も同じブランチへ追加する。

作業ブランチへ最新mainを取り込む場合：

```sh
git fetch origin
git merge origin/main
```

競合時は両方の意図を確認し、相手の変更を一括で上書きしない。未統合の別作業ブランチに依存するときは、先に共通土台を統合するか、PRの依存先・比較元を明示する。

## 6. PRの書き方とレビュー

タイトルはコミットと同じ形式。本文はテンプレートに従い、何ができるようになったか、確認結果、未完了、相手への影響を書く。画面変更は可能ならスクリーンショットを添える。Issueがあればリンクする。

相手は仕様との一致、時間・欠損情報の扱い、秘密情報、担当外の変更を確認する。ビルド・起動等は結果を読み、必要な場合に再現する。承認後にSquash and mergeし、不要になった作業ブランチを削除する。

## 7. GitHub側の推奨設定（未適用）

mainのルールとしてPR必須・相手1人の承認必須・Force Pushと削除の禁止を設定する。コード変更後の承認が古くならない設定も推奨。GitHub ActionsのCheckはpush・pull_request・手動実行に対応し、npm ci・本番ビルド・型チェックを行う。必須チェックには実際に成功したチェックを指定する。現時点ではmainの保護ルールprotect_mainは無効であり、PR・相手の承認・CI成功をGitHub上で必須にする設定は未適用。

これは運用文書の追加であり、リポジトリの保護設定を実際に変更したという意味ではない。GitHub上での設定可否は所有者が確認する。
