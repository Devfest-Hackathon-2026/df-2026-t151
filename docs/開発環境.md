# 共通開発環境とCloud Run

## Vertex AIのADC認証（2026年11月9日更新）

Geminiの生成・Mapsグラウンディング・構造化抽出・再検証はADCを使う。GEMINI_API_KEYは不要。GOOGLE_CLOUD_PROJECTとADC、OPTION_TOKEN_SECRETを準備し、GOOGLE_CLOUD_LOCATIONはglobalを既定とする。以下に残るGeminiキー方式の説明より、この節と[Vertex AI認証設定](VertexAI認証設定.md)を優先する。本番での権限付与・切替は実施記録と区別する。

## Maps系APIの認証方式（2026年11月9日更新）

Places・Routes・Weatherは、Cloud Runで実行アカウントのADCを使うservice-account方式に対応した。GOOGLE_MAPS_AUTH_MODE=service-accountとGOOGLE_CLOUD_PROJECTを指定する。GeminiはADCへ移行し、OPTION_TOKEN_SECRETは引き続き必要。以下に残るMapsキーの説明はapi-key方式の場合に適用する。セットアップ・ローカルADC・本番切替の手順は[Maps認証設定](Maps認証設定.md)を参照する。公開結果はCloudRun公開手順.mdへ別途記録する。

## 採用構成

ユーザー承認：TypeScript、Next.js App Router、Tailwind CSS、Node.js、Cloud Run。DBは初版では使わない。Node.jsは24.22.2 LTSに固定し、Dockerfile・.nvmrc・package.json・package-lock.jsonで版を揃える。24.22.2には10月21日のセキュリティ修正が含まれる。[Node.js公式のセキュリティ情報](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)

開発はDocker Composeで揃える。各自がDocker DesktopのLinuxコンテナを使い、ホスト側のNode・npmは必須にしない。VS Code利用者はDev Containersで同じコンテナに入る選択肢もある。ローカルのCodexは通常の作業フォルダからファイル編集できる。

## 2人の初回操作

1. Docker Desktopを起動する。Windowsで必要ならWSL 2の設定を完了する。
2. リポジトリを取得し、共有されたブランチをチェックアウトする。
3. リポジトリのルートで `docker compose up --build` を実行する。
4. `http://localhost:3000` を開く。終了はCtrl+C、停止・片付けは `docker compose down`。

最初の起動時はイメージとパッケージの取得に時間がかかる。node_modulesと.nextはコンテナ用ボリュームに隔離する。ホスト側と混ぜない。開発起動時にnpm ciするため、ロックファイルの変更も反映される。

Node.jsの版が更新されたら、`docker compose up --build` で開発用イメージを再構築する。GitHub Actionsは .nvmrc を参照する。

VS Codeでは「Dev Containers: Reopen in Container」で開き、コンテナ内で `npm run dev` を実行できる。通常のCompose起動と重ねて同じポートのサーバーを起動しない。

## 確認コマンド

```sh
docker compose exec app npm test
docker compose exec app npm run typecheck
docker compose exec app npm run build
```

ビルドで開発中の.nextが変わるため、動作が乱れたら開発サーバーを再起動する。GitHub Actionsでも別環境でnpm ci・ビルド・型チェックする。

APIの自動テストは固定したNode.jsの標準テストランナーとTypeScript型除去で実行する。追加のテスト依存は入れず、型の正しさは別途typecheckで確認する。サーバー内部の実行時importは相対パスと.ts拡張子を使用し、tsconfigのallowImportingTsExtensionsで型チェックと両立させる。CIでもnpm testを実行する。

## コードの整形

Prettier 3.9.10を開発依存として版固定で導入した。[公式の導入手順](https://prettier.io/docs/install)に従い、package-lock.jsonと共に管理する。設定はルートの.prettierrc.jsonで、シングルクォート・行幅の目安100文字・改行LFを指定する。その他はPrettierの標準設定を使う。

.gitattributesでもテキストの改行をLFに揃え、WindowsでのチェックアウトによるCRLFへの変換を防ぐ。この導入では既存ファイルの改行を一括変換しない。

```sh
# 整形する（リポジトリ全体を書き換えるため、作業差分を確認してから実行）
docker compose exec app npm run format
# 整形が必要なファイルを確認する（書き換えなし）
docker compose exec app npm run format:check
# 個別ファイルだけを整形する例
docker compose exec app npm exec -- prettier src/server/grounded-detours.ts --write
```

ルートで実行すると.gitignoreと.prettierignoreを参照する。生成物・依存・ロックファイル・ローカル秘密設定は整形対象から外す。導入時点では既存コード・文書の一括整形は未実施なので、format:checkは既存の整形差分により終了コード1となる。全体整形とCIへの整形チェック追加は次の工程とする。機能の変更や関数分割は整形とは別のコミットで行う。

参考：[Node.jsのTypeScript実行](https://nodejs.org/docs/latest-v24.x/api/typescript.html)、[標準テストランナー](https://nodejs.org/docs/latest-v24.x/api/test.html)。

本番コンテナの確認：

```sh
docker build --platform linux/amd64 -t yorimichi:local .
docker run --rm -p 8080:8080 -e PORT=8080 yorimichi:local
```

`http://localhost:8080` と `/api/health` を確認する。Composeのdevステージはホットリロード用、本番はstandalone出力だけを含むrunnerステージ。共通のNode版とロックファイルを使うが、開発サーバー自体を本番には持ち込まない。

## 秘密設定

.env.exampleで変数名だけ共有する。実値は.env.local（Git対象外）または本番のSecret Managerへ。Next.jsは.env.localを読む。NEXT_PUBLIC_を秘密鍵に付けない。Dockerビルド時に.envやキーを取り込まない。

場所検索を試す場合はGoogle CloudでPlaces API (New)と請求設定を準備し、サーバー用のGOOGLE_MAPS_API_KEYを.env.localへ設定して開発サーバーを再起動する。キーにはPlaces APIのAPI制限と、実行環境に合うアプリケーション制限を設定する。秘密の値をGitHubやチャットへ貼らない。Text Searchの取得項目はPro区分を含むため、利用量・割当を確認する。

候補探索にはGEMINI_API_KEYへAgent PlatformのAPIキー方式のキーを設定する。サーバーは固定のグローバルエンドポイントでGemini 3.5 FlashとGoogle Maps groundingを利用する。Google AI StudioのDeveloper APIキーや通常プロジェクトのADCと接続方法を混同しない。APIの有効化だけでは認証設定は完了しない。今回の実接続ではユーザーがローカルに設定し、キーを表示せず200を確認した。通常プロジェクト・ADCへの接続は今回の実装対象外。

キーを含まない確認用URL： `http://localhost:3000/api/v1/places?requestId=manual-check&query=%E6%96%B0%E5%AE%BF%E9%A7%85` 。これは実APIを1回呼ぶ。候補0件の正常応答と、設定不足・外部障害のエラーを区別する。通常の `http://localhost:3000/` がサーバーAPIを使う画面で、架空デモやモード切り替えはない。キーが未設定・外部障害の場合はエラーを表示し、架空候補へ代替しない。

候補検索・行程再検証にはOPTION_TOKEN_SECRETも必要。32バイト以上の乱数を16進文字列等にして、32〜256文字・空白なしのサーバー秘密設定として.env.localまたはSecret Managerへ置く。今回のローカル確認では生成した値をGit対象外の.env.localに追加した。実値を画面・チャット・Git・ログへ出さない。複数インスタンスは同じ値を使い、変更すると既発行トークンが無効になる。共有するのは変数名と設定手順だけでよく、AにGoogleキーや署名秘密値を渡す必要はない。Aが独立環境で実APIを試す場合は、そのサーバー用の権限・秘密設定を別途準備する。

公開前に、画面でのGoogle Maps・第三者提供元の帰属表示、利用規約・プライバシーポリシー、共有の呼出上限、プラットフォームのHTTPアクセスログに検索クエリを残さない設定を確認する。アプリ内の上限はプロセスごとで、費用の全体上限ではない。

Next.jsの開発用アクセスログでは場所検索のパスを除外する設定をnext.config.tsへ追加した。[公式のlogging設定](https://nextjs.org/docs/app/api-reference/config/next-config-js/logging)を使用し、検索語をコンソールへ残さない。本番のリバースプロキシ・Cloud Run等のログ設定は別途必要。

徒歩経路の内部処理にも同じGOOGLE_MAPS_API_KEYを使う。キーが所属するGoogle CloudプロジェクトでRoutes APIを有効化し、キーのAPI制限でPlaces API (New)とRoutes APIの両方を許可する。請求設定と実行環境に合うアプリケーション制限も確認する。設定変更直後は反映を待って確認する。

訪問時間帯の予報には、同じサーバー用GOOGLE_MAPS_API_KEYでWeather APIを利用する。キーが所属するプロジェクトでWeather APIを有効化し、キーのAPI制限でも許可する。請求設定も確認する。今回の実接続は初回403だったが、ユーザーによる設定の見直し後に200を確認した。候補がない場合は天候取得を省略するため、検索結果のweather.status=unknownだけでキー設定の成否を判断しない。確認済み範囲は検証結果.mdを参照。

経路処理はcomputeWalkingRoute・getDirectJourneyを候補検索・行程再検証APIから利用する。実接続は公開地点を使い、正確なユーザー位置や経路の生応答を通常ログ・リポジトリへ記録しない。自動テストでは外部通信を差し替えるため、実キーや課金設定は不要。

候補の取得はGeminiのMaps探索→構造化抽出の最大2呼出で行い、その後に目的地Details1回・候補Details最大4回・Routes最大9回で検証する。再検証はGemini最大2呼出・選択地点と目的地Details各1回・Routes最大3回。Geminiの2段階は合計18秒、各処理全体25秒。Placesの現在営業時間はEnterprise区分の項目を含む。Geminiの生成・Maps groundingは別途課金対象で、Mapsツール内の検索回数は複数になる場合がある。両POSTの枠は1プロセス20件/分・同時2処理で、各サービスの割当や複数インスタンスの合計上限は別途管理する。

目的地内施設の修正後は、入場せず目的地の外から利用できる出典付き根拠も必要とする。Placesの包含情報が欠落しているだけでは根拠にしない。Geminiの元回答・Mapsの出典・抽出した利用条件を照合し、出典や条件不明は除外する。モデルや外部情報の正確さ・現地利用・到着を保証するものではない。検証結果と制約は検証結果.md、詳細はAPI入出力仕様.mdを参照する。

## Cloud Runへの公開準備

公式のNext.js向けCloud Run手順がある。今回のDockerfileはLinux向け、0.0.0.0への待受、PORT、standalone起動に対応する。本番の外部APIはサーバー側で呼び出す。

公開にはGoogle CloudプロジェクトID、請求設定、有効なAPI、デプロイ権限、実行サービスアカウントと秘密設定が必要。本番はgdgoc-hackathone-2026の東京リージョンへ公開済み。実際の設定・秘密参照・更新用コマンドは[Cloud Run公開の作業記録](CloudRun公開手順.md)を参照。以下は初期準備時の一般的な非公開デプロイ例。

Google Cloud CLIを準備したローカルまたはCloud Shellで、リポジトリのルートから次を実施する。YOUR_PROJECT_IDは実際のIDに置き換える。

```sh
gcloud run deploy yorimichi --source . --project YOUR_PROJECT_ID --region asia-northeast1 --port 8080 --memory 512Mi --cpu 1 --min-instances 0 --max-instances 2 --no-allow-unauthenticated
```

既存DockerfileをCloud Buildでビルドするため、ローカルDockerがなくても公開できる。API有効化・ビルド権限・課金の要件は公式手順で確認する。初回は非公開で実行確認し、審査員がログインせず開ける公開設定への変更は提出前に行う。上限2台は費用の完全な上限ではなく、外部APIの割当・アプリの呼び出し制限・予算通知も別途必要。

API接続後は専用実行アカウントへ必要最小限の権限を付け、Secret Managerから渡す。キーの実値をコマンド履歴やGitHubに載せない。公開後、healthだけでなく実際の検索も確認する。

## 採用理由と制約

同じNode・依存関係・OS環境を再利用でき、経験の少ないメンバーの導入操作を揃えられる。一方Dockerは初回取得とメモリを使い、Windowsのファイル共有では更新が遅い場合がある。必要ならWSL内への配置を検討するが、現時点で作業フォルダを勝手に移動しない。ローカルNodeによる開発も可能だが、まずComposeを共通手順とする。

## 検証再開・完了

依存パッケージの版固定とpackage-lock.jsonの生成、本番ビルド、型チェック、開発／本番Docker起動を確認した。現在は初回操作のdocker compose up --buildで起動できる。GitHub Actionsはpush・pull_request・手動実行に対応する。GitHub上の実行結果は別途確認する。

Windows共有フォルダの変更検知が反映されない問題を再現したため、開発時はWebpackとWATCHPACK_POLLING=1000を使用する。本番ビルドはTurbopackのまま。約1秒間隔のファイル監視には追加CPU負荷があるが、手動再起動を避けられる。

検証内容と未確認範囲は検証結果.mdを参照。ホストへ直接node_modulesを展開する手順は採用せず、依存追加もComposeコンテナ内で行う。

```sh
docker compose exec app npm install --save-exact PACKAGE_NAME
```

## 天候による候補選定

weather.tsは表示用の予報と内部の適合性判定を返し、weather-policy.tsに対応コード・降水確率による方針を集約する。visit-forecasts.tsは候補別の取得上限・共有の時間予算を管理し、weather-selection.tsは副作用なしで天候による除外・並び替え・説明を組み立てる。

候補検索は時間条件を満たす最大4件の予報を最終3件への絞り込み前に取得する。Weather APIの上限は従来の検索1回から最大4回へ増え、同時2件・合計1.5秒で制限する。再検証は最大1回。予報待ち後には時間条件を計算し直す。予報の欠落・タイムアウト時の順位維持と警告、時刻の時間枠またぎは回帰テストで確認する。詳細・未対応の屋内候補はAPI入出力仕様.mdを参照する。
